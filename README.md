# Smart Credit — backend

Backend учебного кабинета предпринимателя. Сохраняет заявку в SQLite, передаёт синтетические финансовые показатели отдельному scoring-сервису, хранит результат проверки, подтверждение условий и запись о зачислении на **учебный счёт**. Менеджер не участвует в типовом сценарии.

Это прототип для хакатона. Он не отправляет заявку в банк, не подписывает юридический договор и не переводит реальные деньги. Суммы, одобрение и условия создаются учебными правилами. Ставка **20% годовых** используется только для иллюстративного аннуитетного расчёта и не является ставкой Альфа-Банка или индивидуальным предложением.

## Запуск

Нужен Python 3.12+ без сторонних библиотек. Сначала запустите сервис из репозитория scoring на порту 8001, затем:

```sh
python3 -m backend.app
```

По умолчанию backend слушает `127.0.0.1:8000`, использует `data/applications.sqlite3` и обращается к `http://127.0.0.1:8001/v1/score`. Параметры меняются переменными `HOST`, `PORT`, `DB_PATH`, `SCORING_URL`. В Docker можно задать `HOST=0.0.0.0`, `DB_PATH=/data/applications.sqlite3`, `SCORING_URL=http://scoring:8001`.

Проверка: `GET http://127.0.0.1:8000/health`.

## API

Все ответы — JSON, статусы и события сохраняются в SQLite. Для локального frontend доступен CORS с `localhost` и `127.0.0.1`.

Контракты запроса и ответа scoring находятся в `contracts/scoring.schema.json` и `contracts/scoring-response.schema.json` и синхронизированы с scoring-репозиторием.

| Метод и маршрут | Назначение |
| --- | --- |
| `GET /api/v1/profiles` | Названия четырёх учебных компаний |
| `POST /api/v1/applications` | Отправить заявку, статус `submitted` |
| `GET /api/v1/applications/{id}` | Получить заявку после обновления страницы |
| `GET /api/v1/applications` | Список заявок |
| `POST /api/v1/applications/{id}/evaluate` | Запросить автоматическое решение |
| `POST /api/v1/applications/{id}/accept` | Подтвердить учебные условия |
| `POST /api/v1/applications/{id}/disburse` | Записать зачисление на учебный счёт |

Создание заявки:

```json
{
  "profile_id": "shop",
  "goal_id": "stock",
  "goal_description": "",
  "product_id": "turnover",
  "amount": 1500000,
  "term_months": 12,
  "contact_name": "Алия Соколова",
  "contact_role": "Владелец бизнеса"
}
```

`goal_id`: `stock`, `expenses`, `seasonal`, `equipment`, `upgrade`, `other`. Для `other` нужен `goal_description` минимум из четырёх символов. `product_id`: `turnover` или `investment`. Подтверждение условий принимает `{"accepted": true}`; без явного подтверждения `signed` недоступен.

Ответы создания и дальнейших действий возвращают полную заявку. Важные поля: `id`, `status`, `events: [{status, at, title}]`, `decision`, `score`, `approved_amount`, `reasons`, `factors`, `offer`, `acceptance`, `receipt`, `simulation: true`. `offer` содержит `amount`, `term_months`, `annual_rate_percent`, `monthly_payment`, `total_payment`, `overpayment` и `illustrative: true`. `receipt` содержит `transaction_id`, `credited_at`, `account_masked`, `amount`, `simulation: true`. Ошибки: `{error, message}`, текст `message` на русском.

Путь статусов: `submitted → processing → approved | counter_offer | rejected → signed → funded`. После `rejected` подтверждение невозможно. Повторные вызовы `evaluate`, `accept`, `disburse` после успешного перехода возвращают сохранённый результат. Повторное `disburse` не создаёт вторую запись о зачислении. Если scoring временно недоступен, заявка остаётся в `processing`, появляется `evaluation_error`, а `evaluate` можно безопасно повторить.

## Проверка

```sh
python3 -m unittest discover -s tests -v
python3 -m json.tool contracts/scoring.schema.json
python3 -m json.tool contracts/scoring-response.schema.json
```

Тесты проверяют успешный путь, альтернативную сумму, отказ, ошибочные переходы, сохранение после перезапуска, повторное зачисление, восстановление после недоступности scoring и HTTP-контракт.

## Go backend — этап 6.1: отправка заявок и предварительные проверки

Go backend расположен в корне этого репозитория рядом с сохранённым Python-прототипом.
Он запускается отдельно, по умолчанию на порту **8080**, и предоставляет probes и
демонстрационную авторизацию OTP/JWT, сведения о своей компании, каталог продуктов
и объяснимый предварительный подбор финансирования, а также сохранение кредитных
черновиков, их истории и приватных документов. Заполненную заявку можно отправить:
предварительные проверки выполняет worker того же процесса. Контракт Go отличается
от описанного выше Python-прототипа: создание сохраняет `draft`, отдельный submit
запускает обработку, после проверок заявка остаётся в `processing` и ожидает scoring.

Архитектура: один процесс `net/http` + chi, структурированные JSON-логи `log/slog`,
пул PostgreSQL `pgx/v5/pgxpool`. Конфигурация загружается из ENV с проверкой значений.
При старте выполняется проверка подключения к БД; ошибка конфигурации, подключения
или занятого порта завершает процесс с ненулевым кодом. SIGINT/SIGTERM запускают
graceful shutdown HTTP и worker, затем закрывается пул. DSN и секреты не выводятся в логи.

```text
cmd/api/             точка входа, сигналы, жизненный цикл сервера и пула
internal/config/     ENV и валидация
internal/auth/       OTP, JWT, роли, контекст текущего пользователя
internal/company/    сведения о собственной компании
internal/credit/     продукты, точные расчёты и предварительные рекомендации
internal/application/ кредитные черновики, валидация и версии
internal/document/   типы документов, приватное файловое хранилище и восстановление загрузок
internal/pipeline/   submit, проверки ФНС/БКИ и ограниченный фоновый worker
internal/httpapi/    chi, middleware, probes и HTTP handlers
internal/postgres/   pgxpool, пользователи, OTP, компании, продукты, заявки, история и документы
migrations/          схема и синтетические данные, golang-migrate
api/openapi.yaml     полный контракт реализованных Go API
api/postman/         единая коллекция автоматических API-проверок
```

HTTP-клиент `scoring` зарезервирован под следующий этап. Worker находится в
`internal/pipeline` и запускается в том же процессе, отдельный сервис не требуется.

### Запуск через Docker Compose

Нужны Docker Engine и Docker Compose. Все команды выполняются из `smart-credit-backend`.

```sh
docker compose up -d --build
```

Создавать `.env`, вручную запускать миграции и генерировать JWT-секрет не нужно.
Compose ожидает готовности PostgreSQL, запускает одноразовый `migrate up` с
существующим seed и только после его успешного завершения запускает backend.
Backend в режиме `demo` создаёт криптографически случайный JWT-секрет, если он
ещё не задан, затем запускает HTTP-сервер. Healthcheck контейнера проверяет `/ready`.
Команда запуска возвращает управление до завершения healthcheck; готовность видна
через `docker compose ps`.

```sh
docker compose ps
curl -i http://localhost:8080/health
curl -i http://localhost:8080/ready
docker compose logs backend
```

Повторный `docker compose up -d --build` применяет только недостающие миграции;
начальные пользователи, компании и продукты не дублируются. Завершённый `migrate` с кодом `0`
в списке контейнеров — нормальное состояние одноразового сервиса.

Настройки можно переопределить через ENV или существующий `.env`. Пользовательский
`.env` не перезаписывается. `.env.example` описывает доступные настройки и не
требуется для запуска. При использовании уже существующего PostgreSQL volume
сохраняйте его исходные учётные данные: смена переменной пароля не меняет пароль
в уже инициализированной БД.

Используются закреплённые теги образов: Go `1.26.10-alpine3.24`, runtime Alpine
`3.24.3`, PostgreSQL `17.11-alpine3.24`, golang-migrate `v4.20.1`.
Приложение в контейнере работает без root. Порты PostgreSQL и HTTP публикуются только
на `127.0.0.1`. Данные БД, документы и JWT-секрет находятся в отдельных
именованных volumes. Встроенные учётные данные PostgreSQL предназначены только
для изолированной локальной демонстрации.

Секрет хранится в volume `jwt_secrets` в файле
`/var/lib/smart-credit/secrets/jwt-secret`. Файл имеет права `0600`, каталог — `0700`;
контейнер использует его от непривилегированного пользователя. Секрет не попадает в
Git и логи, сохраняется при обычном перезапуске и `docker compose down`.
Явно заданный непустой `JWT_SECRET` имеет приоритет и должен содержать не менее
32 байт. В режиме `production` обязателен явно заданный секрет: генерация и
использование сохранённого demo-файла отключены. Для такого запуска также
необходимо переопределить демонстрационные учётные данные PostgreSQL.

```sh
docker compose stop
docker compose start
docker compose down
```

`down` сохраняет volumes. Для удаления тестовых данных нужна отдельная осознанная
операция удаления volumes. Scoring в этом Compose пока отсутствует.

### ENV и локальный запуск Go

Для сборки нужен Go 1.26+. `.env` автоматически читает Compose; Go-приложение
самостоятельно dotenv-файлы не загружает. Локальный запуск Go по умолчанию
использует `APP_ENV=production` и требует явный `JWT_SECRET`. Для изолированной
демонстрации вне контейнера можно выбрать `demo`:

```sh
docker compose up -d postgres
docker compose run --rm migrate up
APP_ENV=demo \
  DATABASE_URL='postgres://smart_credit:smart-credit-demo-local-only@127.0.0.1:5432/smart_credit?sslmode=disable' \
  go run ./cmd/api
```

Это отдельный вариант для разработки; основной запуск через Compose остаётся
одной командой. Для существующей БД подставьте её локальный DSN. При необходимости
загрузите доверенный shell-совместимый `.env` самостоятельно. Не запускайте
локальный Go и Compose backend одновременно на одном HTTP-порту.

| ENV | Значение по умолчанию / назначение |
| --- | --- |
| `APP_ENV` | Go: `production`, Compose: `demo`; в `production` нельзя автоматически создавать JWT-секрет |
| `HTTP_HOST`, `HTTP_PORT` | `127.0.0.1`, `8080`; Compose задаёт host `0.0.0.0` |
| `HTTP_READ_HEADER_TIMEOUT` | `5s` |
| `HTTP_READ_TIMEOUT`, `HTTP_WRITE_TIMEOUT` | `10s`, `15s` |
| `HTTP_IDLE_TIMEOUT`, `HTTP_SHUTDOWN_TIMEOUT` | `60s`, `15s` |
| `DATABASE_URL` | Обязательный PostgreSQL DSN, без значения в Go-коде |
| `DB_MAX_CONNS`, `DB_MIN_CONNS` | `10`, `2`; min не больше max |
| `DB_CONNECT_TIMEOUT`, `DB_PING_TIMEOUT` | `5s`, `2s`; ping меньше HTTP write timeout |
| `DB_MAX_CONN_LIFETIME`, `DB_MAX_CONN_IDLE_TIME` | `1h`, `15m` |
| `AUTH_DB_TIMEOUT` | `3s`; таймаут операций авторизации, компаний, продуктов, заявок и документов в PostgreSQL, меньше `HTTP_WRITE_TIMEOUT` |
| `LOG_LEVEL` | `info`; также `debug`, `warn`, `error` |
| `DOCUMENT_STORAGE_PATH` | `./data/documents`; приватный каталог файлов, в Compose фиксирован внутри постоянного volume |
| `SCORING_URL` | `http://127.0.0.1:8001`; пока не используется |
| `JWT_SECRET` | Не менее 32 байт для HS256; обязателен в `production`, в `demo` пустое значение включает генерацию; не хранить в Git |
| `JWT_SECRET_FILE` | Локальный Go: `./data/secrets/jwt-secret`; Compose фиксирует `/var/lib/smart-credit/secrets/jwt-secret` в постоянном volume |
| `JWT_ISSUER` | `smart-credit-backend`; проверяется при каждом запросе с JWT |
| `JWT_AUDIENCE` | `smart-credit-frontend`; проверяется при каждом запросе с JWT |
| `DEMO_OTP_CODE` | `1234`; четыре цифры, сравнение на backend, реальные SMS не отправляются |

В Compose DSN строится из `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB` и host
`postgres`; локальный `DATABASE_URL` из `.env` не подставляется в контейнер. Пароль
в этой простой конфигурации должен состоять из URL-safe символов. `POSTGRES_PORT`
меняет локальный порт БД; при его изменении обновите локальный DSN. Внутри Compose
путь документов фиксирован: `/var/lib/smart-credit/documents`, scoring URL по
умолчанию `http://scoring:8001` зарезервирован для будущей интеграции.

### Миграции и начальные данные

`000001` создаёт 11 прикладных таблиц: `companies`, `users`, `otp_challenges`,
`credit_products`, `applications`, `application_events`, `credit_decisions`,
`offers`, `documents`, `jobs`, `idempotency_keys`.

Используются UUID, внешние ключи, ограничения статусов и сумм, индексы очереди и
истории, версии заявок и предложений. Неполные черновики разрешены. Для отправленных
заявок обязательны финансовый и продуктовый снимки JSONB. Результат scoring
сохраняется в `jobs`, окончательное решение backend — в `credit_decisions`.
У задач предусмотрены повторные попытки, время следующего запуска и аренда с токеном.
Техническая ошибка задачи отделена от кредитного отказа. Подтверждение хранится в
`applications` со ссылкой на своё предложение; таблиц выдачи кредита нет.

`000002` добавляет **три синтетические компании**, по одному CLIENT на компанию и
одного BANK_EMPLOYEE без компании. Телефоны тестовых пользователей:
`+79990000001`, `+79990000002`, `+79990000003`, `+79990000004` (сотрудник).
Эти профили доступны для демонстрационного входа. SQLite не импортируется.

`000003` добавляет `otp_challenges.invalidated_at` для отзыва предыдущих активных
подтверждений пользователя. Старые миграции не изменены. При откате этой миграции
отозванные challenge получают исчерпанный лимит попыток, чтобы не стать снова
пригодными после удаления поля отзыва.

`000004` расширяет существующую `companies` юридическими и контактными полями,
а `credit_products` — целями и минимальным возрастом бизнеса. Даты регистрации,
ИНН, ОГРН/ОГРНИП, ОКВЭД и контакты трёх компаний синтетические: API не подтверждает
существование организации в государственном реестре. Действующие кредитные платежи
берутся из прежнего поля `monthly_debt_payments`, без параллельного источника данных.

`000005` заполняет два согласованных продукта — `turnover` и `investment` —
через `INSERT ... ON CONFLICT`. Существующий внутренний UUID продукта сохранён,
в API используется стабильный строковый `code` как `id`. Новые таблицы не создаются;
старые применённые миграции не изменены.

`000006` расширяет существующую `applications` nullable-полями среднемесячной
выручки и расходов, добавляет индексы пагинации по владельцу, компании и статусу.
Ограничения статусов заявок и событий используют `signed`, добавлен `closed`;
прежний `confirmed` преобразуется в `signed`. Прежний `processing_failed`
преобразуется в `processing`, а техническая ошибка сохраняется отдельно в
`processing_error`. Поля подтверждения переименованы в `signed_by`/`signed_at`.
Переходы кредитного конвейера и подписание этим не реализуются. Миграции
`000001`–`000005` не изменены; новые таблицы не создаются.

`000007_document_types` добавляет в существующую `documents` поле `document_type`
и ограничения типов, MIME, размера и безопасного ключа хранения. Прежние поля
состояния загрузки, SHA-256, имени, автора и времени переиспользуются. Непроверенные
прежние метаданные помечаются `failed`. Новые таблицы не создаются.
Метаданные и двоичные файлы хранятся раздельно;
существующие миграции `000001`–`000006` сохранены.

`000008_submission_prechecks` расширяет существующие таблицы для submit и worker:
частные серверные сведения об источнике финансов и демонстрационном статусе
регистрации компании, состояние `jobs.awaiting_scoring` и JSONB-результаты проверок.
Финансовый снимок и версия условий продукта сохраняются при отправке, дальнейшее
изменение снимков запрещает PostgreSQL. Новые таблицы не создаются; миграции
`000001`–`000007` сохранены.

При обычном запуске миграции выполняются автоматически. Для диагностики и
осознанного управления схемой по-прежнему доступны CLI-команды:

```sh
docker compose run --rm migrate version
docker compose run --rm migrate up        # повторный запуск: no change
docker compose run --rm migrate down 1    # только 000008; выполнять в отдельной тестовой БД
docker compose run --rm migrate up 1      # восстановить 000008 перед запуском backend
```

Полный откат в пустой тестовой БД: `docker compose run --rm migrate down 8`.
Откат `000006` удаляет новые финансовые поля; выполняйте его только осознанно.
Если новые состояния нельзя представить в прежней схеме, откат завершается ошибкой
вместо удаления несовместимых записей.
Откат seed откажет, если на demo-пользователей уже ссылаются заявки или OTP: данные не
удаляются каскадно. Для локально установленного golang-migrate v4.20.1 доступен
эквивалент: `migrate -path ./migrations -database "$DATABASE_URL" up`.
golang-migrate создаёт собственную служебную таблицу `schema_migrations`.

Submit и worker меняют статус и добавляют события в одной транзакции. Снимки
копируются при submit, результат worker фиксируется только при совпадении токена
аренды и действующей lease. Бизнес-проверки находятся в Go; ограничения PostgreSQL
защищают целостность и неизменяемость уже отправленных данных.

### Проверки Go

```sh
go mod tidy
go fmt ./...
go vet ./...
go test ./...
go build ./...

# Дополнительно: отдельная тестовая PostgreSQL, включая конкурентные OTP/PATCH/submit.
TEST_DATABASE_URL="$DATABASE_URL" go test -v ./...
docker compose build backend
```

Unit-тесты проверяют конфигурацию, probes, таймаут readiness, безопасные ошибки,
JWT, auth handlers, middleware, возраст компании, аннуитет, доступную сумму,
округление и ограничения подбора, частичные черновики, nullable PATCH, ограничения
продуктов, версии, доступ владельца и роли. PostgreSQL-тесты проверяют компании, активные
продукты, параметризованные запросы и реальные операции OTP,
включая истечение, ограничение попыток, одноразовость, замену challenge и
конкурентный verify, атомарность создания/изменения заявки и события, SQL-пагинацию,
фильтры, историю, конкурирующие PATCH/submit, захват задач, lease, повторы и
восстановление обработки. Они используют отдельную временную схему, применяют миграции
и удаляют её после проверки; существующие прикладные данные не затрагиваются.
Тесты с реальной БД пропускаются, если `TEST_DATABASE_URL` не задан.
В Go-задаче CI PostgreSQL запускается автоматически, а `TEST_DATABASE_URL` задан,
поэтому тесты конкурентных OTP-операций выполняются и в CI.
Существующие Python-тесты запускаются прежней командой из раздела выше.

Проверка потери БД на работающем backend:

```sh
docker compose stop postgres
curl -i http://localhost:8080/health  # 200: процесс жив
curl -i http://localhost:8080/ready   # 503: БД недоступна
docker compose start postgres
curl -i http://localhost:8080/ready   # 200 после восстановления PostgreSQL
```

`/ready` проверяет соединение с БД, а не версию миграций. `/health` не зависит от БД.

### Postman Collection и Newman

Коллекция [api/postman/smart-credit-stage2-postman-collection.json](api/postman/smart-credit-stage2-postman-collection.json)
использует Postman Collection v2.1. Импортируйте её в Postman и запустите целиком
через Collection Runner. `baseUrl` по умолчанию — `http://localhost:8080`.
Профили клиентов и сотрудника, OTP challenge и access token передаются между
запросами автоматически; ручное копирование не требуется. Код `1234` соответствует
демонстрационной конфигурации по умолчанию.

Если Newman установлен, тот же набор запускается из корня backend:

```sh
newman run api/postman/smart-credit-stage2-postman-collection.json \
  --working-dir api/postman

# Другой адрес уже запущенного backend:
newman run api/postman/smart-credit-stage2-postman-collection.json \
  --working-dir api/postman \
  --env-var baseUrl=http://localhost:18080
```

При отсутствии локального Newman доступен Docker-вариант для Compose project
`smart-credit` по умолчанию:

```sh
docker run --rm --network smart-credit_default \
  -v "$PWD/api/postman:/etc/newman:ro" \
  --workdir /etc/newman \
  postman/newman:6.1.3-alpine \
  run /etc/newman/smart-credit-stage2-postman-collection.json \
  --env-var baseUrl=http://backend:8080
```

При другом имени Compose project или HTTP-порте укажите соответствующие сеть и
внутренний адрес backend.

Коллекция проверяет probes, выбор профилей, OTP, ошибки авторизации, JWT и текущего
пользователя для обеих ролей. Далее она автоматически авторизует второго клиента
для проверки запрета чужой компании, проверяет собственную компанию, оба продукта,
каталог для обеих ролей и подбор финансирования. Проверяются независимая аннуитетная
формула, округление, бюджет, доступная сумма, ограничения, альтернативы, нулевая
выручка, отрицательный остаток, невалидные поля и запреты доступа. Повторный полный
запуск не требует очистки переменных или ручной передачи токенов и UUID. Далее проверяются создание двух неполных
черновиков, повторное открытие, редактирование, очистка полей через `null`, история,
пагинация и фильтры, версии, изоляция второго клиента и ошибки ролей/входных данных.
`applicationId` и актуальная `version` сохраняются автоматически. Каждая итерация
создаёт новые черновики; существующие записи не нужно удалять.
Затем коллекция создаёт отдельный черновик для документов, загружает PDF, PNG и JPEG,
повторно загружает выписку, проверяет метаданные и SHA-256 скачанных файлов,
изоляцию другого клиента, чтение сотрудником банка и запрет загрузки сотрудником.
Невалидный формат, пустой файл, несоответствие расширения содержимому, multipart,
опасные имена и оба ограничения размера проверяются автоматически. Файлы в
`api/postman/fixtures/` полностью синтетические; большие запросы генерируются
скриптом запроса, отдельный файл размером больше 5 МиБ не нужен. Для Postman
Desktop задайте Working directory в настройках равным `api/postman` этого
репозитория и разрешите чтение файлов коллекции. JWT, applicationId и documentId
передаются автоматически. Завершающие сценарии проверяют submit: неполную заявку,
отсутствующие обязательные документы, успешные оборотный и инвестиционный пути,
повторную отправку, запреты доступа и редактирования после отправки. Timeline
опрашивается автоматически с ограниченным числом повторов до `PRECHECKS_COMPLETED`;
копировать JWT, UUID, версии или ждать вручную не требуется. Каждая итерация
создаёт собственные заявки и проверяет сохранённое состояние `processing`.
Не экспортируйте полученные access token в Git.

При добавлении новых API необходимо обновлять OpenAPI и эту же коллекцию,
добавлять позитивные и негативные сценарии с проверками ответа и автоматической
передачей данных, затем повторно проверять существующие API.

### Демонстрационная авторизация

Все демонстрационные пользователи загружаются из PostgreSQL, включая роль и связь
с компанией. Список профилей и OTP-маршруты публичны. `GET /api/v1/me` требует
Bearer Token. Полный контракт: [api/openapi.yaml](api/openapi.yaml).

| Метод и маршрут | Назначение |
| --- | --- |
| `GET /api/v1/demo/profiles` | Три предпринимателя и один сотрудник из seed |
| `POST /api/v1/auth/otp/request` | Создать challenge по `profileId`, имитировать SMS |
| `POST /api/v1/auth/otp/verify` | Проверить код и выдать JWT |
| `GET /api/v1/me` | Текущий пользователь из PostgreSQL |

Порядок входа:

```sh
curl -sS http://localhost:8080/api/v1/demo/profiles

curl -sS http://localhost:8080/api/v1/auth/otp/request \
  -H 'Content-Type: application/json' \
  -d '{"profileId":"20000000-0000-4000-8000-000000000001"}'
```

Первый профиль имеет следующий вид (в ответе списка он находится в `items`):

```json
{
  "id": "20000000-0000-4000-8000-000000000001",
  "name": "Иван Лавкин",
  "phone": "+79990000001",
  "role": "CLIENT",
  "companyName": "ИП «Лавка у дома»"
}
```

Ответ создания challenge — `201 Created` (идентификатор и время приведены для примера):

```json
{
  "otpRequestId": "30000000-0000-4000-8000-000000000001",
  "expiresAt": "2026-10-23T12:05:00Z",
  "maskedPhone": "+7*** *** 0001"
}
```

Используйте фактический `otpRequestId` из предыдущего ответа:

```sh
curl -sS http://localhost:8080/api/v1/auth/otp/verify \
  -H 'Content-Type: application/json' \
  -d '{"otpRequestId":"<otpRequestId>","code":"1234"}'
```

Ответ успешной проверки — `200 OK`:

```json
{
  "accessToken": "<accessToken>",
  "tokenType": "Bearer",
  "expiresAt": "2026-10-23T20:00:00Z",
  "userId": "20000000-0000-4000-8000-000000000001",
  "role": "CLIENT",
  "companyId": "10000000-0000-4000-8000-000000000001"
}
```

Значение `accessToken` необходимо хранить как секрет; не выводите его в общие логи.
Пример запроса текущего пользователя с подстановкой токена:

```sh
curl -sS http://localhost:8080/api/v1/me \
  -H 'Authorization: Bearer <accessToken>'
```

```json
{
  "id": "20000000-0000-4000-8000-000000000001",
  "name": "Иван Лавкин",
  "phone": "+79990000001",
  "role": "CLIENT",
  "companyId": "10000000-0000-4000-8000-000000000001"
}
```

Для сотрудника используйте профиль `20000000-0000-4000-8000-000000000004`;
его `companyName` в списке и `companyId` в verify/me равны `null`.

OTP действует **5 минут**, допускает **5 попыток** и используется один раз.
Правильный код на пятой попытке допустим. Новый challenge делает предыдущие
активные challenge пользователя недействительными. Проверки и изменение состояния
выполняются транзакционно с блокировками PostgreSQL: параллельные запросы не
могут повторно использовать один OTP или превысить лимит попыток. Симуляция SMS
не вызывает внешние сервисы. Код и JWT не логируются; JWT в БД не сохраняется.

JWT действует **8 часов** и содержит идентификатор пользователя в `sub`.
Authentication middleware проверяет HS256, подпись, обязательный срок действия,
issuer и audience, затем загружает актуального пользователя из PostgreSQL.
RequireRole проверяет роли `CLIENT`/`BANK_EMPLOYEE` из контекста. Роль не принимается
из запроса и не берётся из клиентских JWT claims. Контекст содержит пользователя
и его `companyId` для проверок владельца и компании в API заявок.

Новые API возвращают ошибки в едином формате:

```json
{"error":"invalid_otp","message":"Неверный код подтверждения"}
```

| HTTP | Код / условие |
| --- | --- |
| `400` | `invalid_request` — некорректный JSON/UUID/поля; `invalid_otp` — неверный код |
| `401` | `unauthorized` — нет JWT, неверный, истёкший токен или отсутствующий пользователь |
| `403` | `forbidden` — роль не разрешена или запрошена чужая компания |
| `404` | `profile_not_found`, `otp_not_found`, `company_not_found`, `product_not_found`, `application_not_found`, `document_not_found` |
| `409` | `otp_used`, `otp_invalidated`, `version_conflict`, `invalid_status` |
| `410` | `otp_expired` |
| `413` | `request_too_large` — JSON больше 64 KiB; документ больше 5 МиБ или полный multipart больше 5 МиБ + 64 КиБ |
| `415` | `unsupported_media_type` — неверный тип тела; `unsupported_file_type` — формат документа или расширение не соответствуют содержимому |
| `422` | `validation_failed` — submit нарушает требования полноты, документов или продукта; массив `details` содержит поля и причины |
| `429` | `otp_attempts_exceeded` — исчерпан лимит проверки данного challenge |
| `503` | `service_unavailable` — БД или файловое хранилище недоступны, либо истёк таймаут операции |
| `500` | `internal_error` — непредвиденная ошибка без внутренних подробностей |

Поля тела имеют формат camelCase. Неизвестные поля и несколько последовательных
JSON-значений отклоняются. Заголовок `Cache-Control: no-store` запрещает кеширование
ответов. SQL-запросы параметризованы; операции БД ограничены `AUTH_DB_TIMEOUT`.

### Границы демонстрационной авторизации

Это публичный демонстрационный вход с выбором в том числе сотрудника банка.
Он предназначен для синтетических данных хакатона. Нет реальных SMS, паролей,
refresh token, logout/revocation, отдельного ограничения частоты создания challenge
или промышленного подтверждения владения телефоном. Ограничение пяти попыток
относится к одному challenge; создание нового начинает новый лимит.

Submit и worker выполняют только предварительные проверки; scoring-клиент и
кредитные решения не реализованы. Go не обращается к Python scoring.
Предварительный подбор не записывает решения
или задачи, не создаёт заявки и не изменяет их статусы.


### Компании, продукты и предварительный подбор

Все четыре новых маршрута требуют JWT. Компания определяется по актуальному
пользователю из PostgreSQL; передать свою роль или чужой `companyId` в подбор нельзя.

| Метод и маршрут | Доступ и результат |
| --- | --- |
| `GET /api/v1/companies/{companyId}` | CLIENT, только своя компания; чужая компания и BANK_EMPLOYEE получают `403` |
| `GET /api/v1/credit-products` | CLIENT и BANK_EMPLOYEE; активные продукты из PostgreSQL в `{items: [...]}` |
| `GET /api/v1/credit-products/{productId}` | CLIENT и BANK_EMPLOYEE; публичный код `turnover` или `investment`, неизвестный — `404` |
| `POST /api/v1/recommendations` | CLIENT; предварительный расчёт без сохранения заявки или кредитного решения |

Ответ компании содержит `id`, `name`, `organizationType` (`ИП`/`ООО`), `inn`,
`registrationNumber`, `registrationDate`, `okved`, `directorName`, `contact`,
`financials`, `simulation: true`. В `financials` представлены выручка, расходы,
текущий долг, ежемесячные платежи по нему и количество просрочек. Это синтетические
сведения, разрешённые для показа владельцу компании.

| Продукт | Цели | Сумма, руб. | Срок, мес. | Годовая ставка | Возраст бизнеса |
| --- | --- | --- | --- | --- | --- |
| `turnover` | `stock`, `expenses`, `seasonal` | 100 000–3 000 000 | 6–24 | 22% | от 6 мес. |
| `investment` | `equipment`, `upgrade` | 300 000–10 000 000 | 12–60 | 20% | от 12 мес. |

Условия загружаются из БД и являются демонстрационными. Это **не действующие
условия Альфа-Банка**. `annualRatePercent` — JSON-число, `id` продукта — строковый
код. Суммы и сроки на границах разрешены.

Пример запроса подбора после авторизации:

```http
POST /api/v1/recommendations
Authorization: Bearer <accessToken>
Content-Type: application/json

{
  "purpose": "stock",
  "requestedAmountRub": 1500000,
  "termMonths": 12,
  "monthlyRevenueRub": 2400000,
  "monthlyExpensesRub": 1500000
}
```

Все пять полей обязательны и не принимают `null`. Денежные значения — целые рубли:
запрашиваемая сумма от `1` до `1 000 000 000 000`, выручка и расходы от `0` до
`1 000 000 000 000`. Срок от `1` до `120` месяцев; продуктовые ограничения
проверяются отдельно. Допустимы цели `stock`, `expenses`, `seasonal`, `equipment`,
`upgrade`, `other`. Для `other` оба текущих продукта вернут несоответствие цели.
Неизвестные поля, включая `companyId`, дробные суммы и некорректные значения — `400`.
Корректный запрос без подходящего продукта всегда возвращает `200`.

Финансовая модель:

```text
surplus = monthlyRevenueRub - monthlyExpensesRub
paymentBudget = floor(max(0, 0.5 × surplus - existingMonthlyPaymentsRub))
r = annualRatePercent / 1200
k = r / (1 - (1 + r)^(-termMonths))
monthlyPayment = ceil(requestedAmountRub × k)
availableAmount = min(productMax, floor(paymentBudget / k))
```

При нулевой ставке `k = 1 / termMonths`. Промежуточные вычисления выполняются
точными рациональными числами (`math/big.Rat`), деньги хранятся как `int64`.
Платёж округляется **вверх**, бюджет и доступная сумма — **вниз** до целого рубля.
При нулевой выручке, отрицательном остатке или недостатке средств бюджет равен нулю.
Выручка и расходы берутся из запроса только для текущего расчёта и не меняют БД;
действующие ежемесячные платежи — из компании в PostgreSQL. Возраст — число полных
календарных месяцев в UTC; если исходный день отсутствует в текущем месяце,
используется последний день этого месяца.

Ответ содержит `companyId`, `businessAgeMonths`, `surplusRub`,
`existingMonthlyPaymentsRub`, `paymentBudgetRub`, `products`,
`recommendedProductId`, `disclaimer`, `simulation: true`. Для каждого продукта
возвращаются его условия, флаги `matches` (`purpose`, `amount`, `term`, `businessAge`,
`affordability`), `eligible`, доступная сумма, платёж, массивы `reasons`,
`limitations` и `adjustments`. Каждый вариант корректировки содержит сумму, срок,
платёж и объяснение.

Для первого клиента и запроса выше остаток равен `900000`, действующие платежи —
`90000`, бюджет — `360000` рублей. Рекомендуется `turnover`; инвестиционный продукт
не соответствует цели. Если срок не разрешён продуктом, его `monthlyPaymentRub`
равен `null`, доступная сумма — `0`, а причина отражается в `limitations`.
Доступная сумма сама по себе не означает соответствие цели или возрасту бизнеса.

Только продукт, подходящий исходному запросу по всем пяти флагам, получает
`eligible: true`. При нескольких подходящих выбирается меньший платёж, затем
лексикографически меньший ID. При отсутствии подходящих `recommendedProductId`
равен `null`. Корректировки могут увеличить срок, ограничить сумму лимитами или
уменьшить её до доступной; они проверяются по бюджету и не заменяют параметры
пользователя автоматически. Для выбора корректировки нужно повторить запрос
с изменёнными суммой или сроком.

**Подбор не является кредитным решением и не гарантирует одобрение.** Он не
воспроизводит скоринговую модель и не обращается к Python scoring. Проверка
обязательности документов, кредитный риск, отправка заявок и окончательные решения относятся к следующим
этапам.


### Кредитные заявки и черновики

Все пять операций требуют JWT и роли `CLIENT`. Владелец и компания определяются
по актуальному пользователю из PostgreSQL. Проверяются **оба** значения: список,
карточка, изменение и история доступны только владельцу в его компании. Для чужой
и несуществующей заявки одинаково возвращается `404 application_not_found`.
`BANK_EMPLOYEE` получает `403`, запрос без JWT — `401`.

| Метод и маршрут | Результат |
| --- | --- |
| `POST /api/v1/applications` | `201`, новый неполный черновик и первое событие |
| `GET /api/v1/applications?limit=20&offset=0&status=draft` | `200`, SQL-пагинация `{items, total, limit, offset}` |
| `GET /api/v1/applications/{applicationId}` | `200`, сохранённая заявка с компанией и продуктом |
| `PATCH /api/v1/applications/{applicationId}` | `200`, обновлённый черновик с увеличенной версией |
| `GET /api/v1/applications/{applicationId}/timeline` | `200`, упорядоченная история `{items: [...]}` |

`POST` принимает `{}`. Все семь редактируемых полей необязательны и допускают
`null`: `productId`, `purpose`, `purposeDescription`, `requestedAmountRub`,
`termMonths`, `monthlyRevenueRub`, `monthlyExpensesRub`. `productId` — публичный
код `turnover`/`investment`, а не внутренний UUID. Владельца, компанию, статус,
решение и служебные даты передавать нельзя. Неизвестные поля — `400`.

Пример частичного черновика:

```http
POST /api/v1/applications
Authorization: Bearer <accessToken>
Content-Type: application/json

{
  "productId": "turnover",
  "purpose": "stock",
  "requestedAmountRub": 1500000,
  "termMonths": 12
}
```

```json
{
  "applicationId": "40000000-0000-4000-8000-000000000001",
  "userId": "20000000-0000-4000-8000-000000000001",
  "companyId": "10000000-0000-4000-8000-000000000001",
  "productId": "turnover",
  "purpose": "stock",
  "purposeDescription": null,
  "requestedAmountRub": 1500000,
  "termMonths": 12,
  "monthlyRevenueRub": null,
  "monthlyExpensesRub": null,
  "productName": "Оборотный кредит",
  "status": "draft",
  "version": 1,
  "createdAt": "2026-10-23T12:00:00Z",
  "updatedAt": "2026-10-23T12:00:00Z",
  "submittedAt": null,
  "availableActions": ["edit"]
}
```

Название продукта и даты здесь иллюстративные; фактические значения возвращает
backend. `GET /{applicationId}` дополнительно возвращает `company` в формате API
компании и `product: {id, name}`; `product` равен `null`, если продукт не выбран.
`submittedAt` у черновика равен `null`. `availableActions` содержит только `edit`.

В `PATCH` обязателен текущий положительный `version` и хотя бы одно редактируемое
поле. Отсутствующее поле сохраняется, явный `null` очищает его. Например:

```http
PATCH /api/v1/applications/40000000-0000-4000-8000-000000000001
Authorization: Bearer <accessToken>
Content-Type: application/json

{
  "version": 1,
  "monthlyRevenueRub": 2400000,
  "monthlyExpensesRub": 1500000,
  "purposeDescription": null
}
```

Успешный ответ имеет формат создания с `version: 2` и новой `updatedAt`. Даже
присваивание прежнего значения в непустом корректном PATCH увеличивает версию.
Повторный PATCH с `version: 1` вернёт `409 version_conflict`; frontend должен
загрузить актуальную карточку перед следующим сохранением. Одновременные запросы
с одной версией не перезаписывают друг друга: транзакция блокирует строку заявки,
проверяет владельца, `draft` и ожидаемую версию, затем условно обновляет строку и
добавляет событие. Успевает только один запрос, остальные получают конфликт.
Заявку вне `draft` изменить нельзя (`409 invalid_status`).

Суммы — целые рубли: запрашиваемая сумма `1..1 000 000 000 000`, выручка и расходы
`0..1 000 000 000 000`; срок `1..120` месяцев. Цели: `stock`, `expenses`, `seasonal`,
`equipment`, `upgrade`, `other`. Описание обрезается по краям, должно быть
непустым, без NUL и не длиннее 300 символов Unicode; очистка — через `null`.
При выбранном продукте переданные цель, сумма и срок должны соответствовать его
условиям. PATCH проверяет итоговый черновик: при смене продукта можно одновременно
изменить несовместимые поля или очистить их. Неизвестный/неактивный продукт —
`404 product_not_found`; некорректное значение или несовместимость — `400`.
Все поля заполнять пока не требуется, в том числе описание для `other`; возраст
бизнеса и платёжеспособность при сохранении черновика не оцениваются.

Список сортируется по `createdAt DESC, applicationId DESC`. `limit` по умолчанию
`20`, допустим `1..100`; `offset` по умолчанию `0`, допустим `0..2147483647`.
`total` считает все записи владельца и компании с выбранным статусом до пагинации.
Неизвестные/повторяющиеся параметры и неверные значения — `400`. Параметры
передаются в SQL; данные не загружаются целиком ради подсчёта или пагинации.
Элементы содержат `applicationId`, `productId`, `productName`, `requestedAmountRub`,
`termMonths`, `status`, `version`, `createdAt`, `updatedAt`.

Создание заявки и `draft_created`, обновление и `draft_updated` сохраняются в
соответствующей **единой транзакции** PostgreSQL. При ошибке события откатывается
и изменение заявки. История упорядочена по `sequence`; событие содержит
`eventId`, `eventType`, `sequence`, `status`, `createdAt`, `actorId`, `title`.
Заголовки событий: «Черновик создан» и «Черновик обновлён». Финансовые значения,
OTP и JWT в историю не записываются. Глобальный mutex не используется.

Отправка переводит заполненный `draft` в `submitted`, worker — в `processing`.
Состояния `manual_review`, `approved`, `rejected`, `counter_offer`, `signed`, `closed`
зарезервированы для дальнейших этапов; scoring, решения, предложения и подписание
не реализованы. Сохранение черновика само по себе не создаёт задачу или решение.

### Документы кредитных заявок

Все три операции требуют JWT. Предприниматель работает только с собственной
заявкой в своей компании. Сотрудник банка может читать документы любой заявки
этого демонстрационного банка; отдельной модели подразделений и банковских
организаций пока нет. Загружать документы от имени клиента сотрудник не может.

| Метод и маршрут | Доступ и результат |
| --- | --- |
| `POST /api/v1/applications/{applicationId}/documents` | CLIENT, своя заявка в `draft`; `201` и метаданные |
| `GET /api/v1/applications/{applicationId}/documents` | CLIENT-владелец или BANK_EMPLOYEE; `200`, `{items: [...]}` |
| `GET /api/v1/applications/{applicationId}/documents/{documentId}` | Те же права чтения; `200`, содержимое как attachment |

Загрузка принимает ровно две части `multipart/form-data`: файл `file` и текстовое
поле `documentType`. Допустимы `BANK_STATEMENT` (выписка) и `EQUIPMENT_INVOICE`
(счёт или договор на оборудование). Разрешены несколько документов одного типа,
каждый со своим UUID. Удаление и замена отдельными API не реализованы.

Фактическое содержимое должно быть PDF, PNG или JPEG и соответствовать расширению
`.pdf`, `.png`, `.jpg` или `.jpeg`; заявленному клиентом MIME backend не доверяет.
Пустые файлы запрещены. Размер файла ограничен **5 МиБ (5 242 880 байт)**, полный
HTTP body — **5 МиБ + 64 КиБ (5 308 416 байт)** с учётом полей и multipart-границ.
Ограничение применяется при чтении тела. Неизвестные и повторяющиеся части,
оборванный multipart и опасное исходное имя с путём отклоняются. Клиент не может
выбрать имя файла на диске или ключ хранения.

Пример загрузки после авторизации:

```sh
curl -sS http://localhost:8080/api/v1/applications/<applicationId>/documents \
  -H 'Authorization: Bearer <accessToken>' \
  -F 'documentType=BANK_STATEMENT' \
  -F 'file=@api/postman/fixtures/sample.pdf;type=application/pdf'
```

Ответ `201 Created` (UUID, размер и время приведены для примера):

```json
{
  "documentId": "50000000-0000-4000-8000-000000000001",
  "applicationId": "40000000-0000-4000-8000-000000000001",
  "documentType": "BANK_STATEMENT",
  "fileName": "sample.pdf",
  "contentType": "application/pdf",
  "sizeBytes": 500,
  "uploadedAt": "2026-10-23T12:00:00Z"
}
```

Список возвращает такие же метаданные в `items`, без внутренних путей, ключей
хранения и контрольных сумм. Скачивание возвращает исходные байты с фактическим
`Content-Type`, безопасным `Content-Disposition: attachment`, `Content-Length`,
`X-Content-Type-Options: nosniff` и `Cache-Control: no-store`. Каталог не раздаётся
через статический HTTP-сервер. Для отсутствующей и чужой заявки используется
одинаковый `404 application_not_found`; отсутствующий документ и подстановка UUID
документа другой заявки дают `404 document_not_found`. Загрузка вне `draft` —
`409 invalid_status`; неверные поля/имя/пустой файл — `400`; недопустимый формат
или несоответствие расширения — `415`; превышение размера — `413`.

Файлы находятся в существующем volume `documents` по адресу
`/var/lib/smart-credit/documents`; локальный запуск использует
`DOCUMENT_STORAGE_PATH`. Backend работает без root, ограничивает права каталога
и файлов, генерирует ключи хранения и не пишет содержимое файлов в логи.
Метаданные находятся в PostgreSQL; бинарные данные в БД не сохраняются.

Согласованность обеспечивается состояниями загрузки и компенсацией:

1. Multipart читается с ограничением тела и буфером файла до 5 МиБ. Файловое
   хранилище записывает временный файл того же тома, проверяет формат и SHA-256.
2. В PostgreSQL резервируются метаданные `pending` с проверкой владельца и `draft`.
3. Временный файл атомарно переименовывается в окончательный ключ в пределах тома.
4. После подтверждения файла метаданные переходят в `ready`; только теперь документ
   доступен в API и возвращается успешный ответ.

При ошибке резервирования удаляется временный файл; при ошибке публикации или
активации метаданные переводятся в `failed`, затем удаляются файлы. Если БД
недоступна и исход активации неизвестен, файл сохраняется до восстановления:
его нельзя удалять, пока метаданные могут оставаться `ready`. При старте backend
помечает незавершённые загрузки `failed`, проверяет контрольные суммы готовых
документов и исключает отсутствующие или повреждённые файлы. Временные и
осиротевшие файлы удаляются. Между БД и файловой системой нет общей
транзакции: допустим незавершённый `pending` до восстановления, но он не доступен
пользователю. Повторный HTTP upload создаёт новый документ; после потери ответа
клиент может получить несколько документов одного типа, что разрешено для MVP.

Хранилище рассчитано на **один процесс backend на один файловый том**. Блокировка
каталога запрещает параллельный запуск второго процесса с тем же хранилищем.
Фоновый worker для документов не создаётся. Обычные `docker compose restart backend`,
повторный `up -d --build` и `down` сохраняют документы и метаданные. Не удаляйте
volumes рабочего проекта; проверки чистого запуска выполняйте в отдельном Compose
project со своими HTTP/PostgreSQL-портами. Путь документов и метаданные следует
резервировать совместно.

Функция `document.RequiredTypes(productID, reliableTurnover)` используется при submit:
для `turnover` выписка нужна без достоверного источника финансов; для `investment`
обязателен счёт на оборудование. Источник задаётся доверенными сведениями компании
в PostgreSQL, пользователь не может передать его в JSON. Обязательность не блокирует
частичный черновик. OCR, анализ документов, scoring, решения и подписание
не добавлены. Документы не меняют статус и версию
заявки. В MVP нет антивируса, квот общего объёма и пагинации списка документов;
проверка сигнатуры файла не является проверкой достоверности банковских данных.

### Отправка заявки и надёжная фоновая обработка

`POST /api/v1/applications/{applicationId}/submit` требует JWT роли `CLIENT` и
собственную заявку в своей компании. Тело не требуется; непустое тело отклоняется
с `400 invalid_request`. Отсутствующая и чужая заявка дают одинаковый
`404 application_not_found`, сотрудник — `403`, запрос без JWT — `401`.

Перед отправкой обязательны `productId`, `purpose`, `requestedAmountRub`,
`termMonths`, `monthlyRevenueRub`, `monthlyExpensesRub`; для цели `other` также
нужно описание. Проверяются актуальные цель, сумма, срок и минимальный возраст
компании по продукту. Частичный черновик по-прежнему можно сохранять.

Для `turnover` нужен готовый `BANK_STATEMENT`, кроме профиля с доверенным
серверным источником финансов. В синтетическом seed такой источник `demo_bank_feed`
имеет «Лавка у дома»; два других профиля требуют выписку. Для `investment` нужен
готовый `EQUIPMENT_INVOICE`; выписка для этого продукта не обязательна. Документы
проверяются существующим приватным хранилищем: `pending` не подходит.

Успешная отправка возвращает **202 Accepted**, не ожидая завершения проверок:

```http
POST /api/v1/applications/40000000-0000-4000-8000-000000000001/submit
Authorization: Bearer <accessToken>
```

```json
{
  "applicationId": "40000000-0000-4000-8000-000000000001",
  "status": "submitted",
  "submittedAt": "2026-10-23T12:00:00Z",
  "nextStage": "prechecks"
}
```

Повторный submit в `submitted` или `processing` возвращает `202` и исходный
`submittedAt`. Когда предварительные проверки уже сохранены, `nextStage` равен
`awaiting_scoring`, `status` остаётся `processing`. Новая задача и повторное
событие отправки не создаются. Для остальных несовместимых состояний —
`409 invalid_status`. Гонка с сохранением черновика может вернуть
`409 version_conflict`; загрузите актуальную карточку перед повтором.

Ошибка полноты или условий — `422` с конкретными полями и причинами:

```json
{
  "error": "validation_failed",
  "message": "Проверьте обязательные поля и документы заявки.",
  "details": [
    {
      "field": "documents.EQUIPMENT_INVOICE",
      "code": "required_document_missing",
      "message": "Загрузите счёт или договор на оборудование."
    }
  ]
}
```

Другие коды причин: `required`, `out_of_range`, `unsupported_purpose`,
`product_unavailable`, `business_too_young`, `invalid_value`. Неуспешная отправка
не меняет заявку, её историю и очередь. Внутренние ошибки PostgreSQL или файлового
хранилища скрываются за `503 service_unavailable`.

В одной транзакции submit блокирует строку заявки, повторно проверяет состояние
и версию, сохраняет неизменяемые финансовый и продуктовый снимки, увеличивает
версию, устанавливает `submittedAt`, пишет `APPLICATION_SUBMITTED` и создаёт одну
задачу в существующей `jobs`. Ограничения PostgreSQL и блокировки защищают
параллельные submit и PATCH; глобальный mutex не используется. Уже отправленную
заявку нельзя редактировать или дополнять загрузками.

Worker запускается вместе с HTTP в том же Go-процессе. По умолчанию два слота
опрашивают очередь каждые 500 мс, захват использует `FOR UPDATE SKIP LOCKED`.
Задача получает случайный lease token на 30 секунд; выполнение ограничено
10 секундами. Транзакция не остаётся открытой во время проверок. При захвате
worker переводит заявку в `processing` и добавляет `PROCESSING_STARTED`.

Локальный симулятор ФНС проверяет регистрационные поля и подготовленный статус
компании; сохраняет результат, отдельные проверки, проблемы, коды причин и время
выполнения. Локальный компонент БКИ берёт долг, ежемесячные платежи и число
просрочек из снимка синтетической компании. Значения не меняются случайно.
Отрицательная бизнес-проверка сохраняется для будущего Decision Engine и сама
по себе не означает кредитный отказ.

Результаты сохраняются в `jobs.precheck_results` JSONB вместе с событиями
`COMPANY_CHECK_COMPLETED`, `CREDIT_HISTORY_CHECK_COMPLETED`, `PRECHECKS_COMPLETED`.
Пользовательское событие отправки содержит `actorId` клиента, системные — `null`.
Их порядок и понятные заголовки доступны через существующий timeline. Технические
подробности и сами внутренние результаты через публичный API не выдаются.
Завершённая задача переходит в устойчивое `awaiting_scoring` и исключается из
обычного захвата. Заявка остаётся в `processing`; scoring и фиктивные решения
на этапе 6.1 отсутствуют.

Если процесс завершился до сохранения результата, другой захват после истечения
lease повторит работу из сохранённого снимка. Фиксация результата и повторов
проверяет токен и срок аренды, поэтому старый worker не может перезаписать новый
результат. Повторы не дублируют события. Временная ошибка сохраняет безопасный
код и назначает следующую попытку с задержкой от 1 до 30 секунд. Максимум —
пять попыток; затем задача остаётся в диагностическом состоянии ошибки, заявка
по-прежнему `processing`. Техническая ошибка не превращается в отказ.

При SIGINT/SIGTERM прекращаются новые HTTP-запросы и захваты, текущая работа
останавливается до закрытия пула. Незавершённая аренда остаётся в PostgreSQL и
восстанавливается после истечения; отдельные брокер и микросервис не нужны.
Повторный `docker compose up -d --build` или пересоздание backend сохраняет
заявки, задачи и историю в существующих volumes. Чистый запуск и сценарии сбоя
проверяйте отдельным Compose project, не удаляя пользовательские volumes.

Ограничения этапа: проверки ФНС и БКИ локальные и синтетические, обработка
`awaiting_scoring` добавляется на этапе 6.2, решения — на 6.3. После исчерпания
попыток необходима диагностика оператора; публичного API управления очередью нет.
Ограничение документов на один процесс backend на файловый том сохраняется.
