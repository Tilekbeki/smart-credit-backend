# Интеграция с Python scoring

Проверен локальный исходный Python HTTP-сервис с SCORING_MODEL=logreg_v1.
Сервис собран его исходным Dockerfile, без изменения кода, контрактов, артефакта
или зависимостей. Запросы проходили через Go worker и сохранялись в PostgreSQL;
результат читался через GET /api/v1/applications/{id}/decision.

Артефакт `logreg_v1.json` при проверке: SHA-256
`2c1badc982400edefbd29bd33480b204f6988410d0e642d868943a6de45436ff`.

## Контракт

POST /v1/score, GET /health, внутренний порт 8001. Локальные копии схем находятся
в [contracts/](../contracts/) и синхронизированы с предоставленным scoring.

Все восемь входных полей обязательны, дополнительные запрещены: application_id,
monthly_revenue, monthly_expenses, existing_debt, monthly_debt_payments,
overdue_count, requested_amount, term_months. Деньги — целые рубли 0..10¹²,
запрошенная сумма 1..10¹², срок 1..120, просрочки 0..100; ID — непустая строка
до 100 символов. ИНН, документы и название компании не передаются.

Ответ содержит ровно decision, score, approved_amount, reasons, factors. Score —
целое 0..100, больше означает меньший риск. Reasons — непустой список непустых
строк. Шесть factors обязательны; debt_service_share и existing_debt_to_annual_revenue
допускают null. Отсутствующий фактор не подменяется нулём. Go отправляет только
поля схемы и не воспроизводит логистическую регрессию.

## Четыре воспроизводимых сценария

Общие данные БКИ первого CLIENT: долг 500000, действующий платёж 90000,
просрочек нет. Продукт turnover, срок 12 месяцев, ставка продукта 22%.
Seed-миграции не меняются. Для сценариев создаются новые финансовые декларации,
подтверждаются отдельной банковской операцией и используются в новых заявках.

| Исход Go | Выручка | Расходы | Запрошено | Python decision | Score / риск Go | Python amount | Предложение Go |
| --- | --- | --- | --- | --- | --- | --- | --- |
| approved | 2400000 | 1500000 | 1500000 | approved | 97 / LOW | 1500000 | 1500000 |
| rejected | 600000 | 450000 | 100000 | rejected | 85 / LOW | 0 | нет |
| counter_offer | 600000 | 300000 | 1500000 | counter_offer | 96 / LOW | 809633 | 641064 |
| manual_review | 10000000 | 8800000 | 1400000 | counter_offer | 78 / MEDIUM | 1190000 | нет до сотрудника |

Числа получены от настоящей модели, не из HTTP-заглушки. Значение application_id
не влияет на score. При замене артефакта ожидаемые score нужно перепроверить.
Manual_review имеет достаточный бюджет для ручного одобрения исходных условий;
поэтому этот набор также проверяет decisions/accept/decline в Newman.

Дополнительно проверены HIGH/score=7 и rejected при марже 9%, score=71 и допустимом
платеже. В последнем случае Go применяет обязательный финансовый отказ, а сотрудник
не может обойти его ручным одобрением.

## Найденные различия и исправления Go

- Исходные локальные схемы допускали number для части входных денег. Настоящий
  Python принимает только integer; Go уже использовал int64, схемы уточнены.
- Уточнены непустой application_id и minLength причин. Декодер Go проверяет их.
- Невозможность обслуживать минимум продукта при LOW теперь проверяется раньше
  advisory-конфликта. Score=85 с нулевым бюджетом даёт финансовый отказ.
- Go-demo-v2 явно проверяет положительный поток, маржу ≥10%, менее трёх просрочек
  и долг <150% годовой выручки. Эти ограничения действуют и для ручных предложений.
- Исторические оценки go-demo-v1 сохраняют читаемость и не пересчитываются.

Python оценивает платёж по условным 20%; Go использует ставку снимка продукта.
Это намеренное различие, а не несовместимость JSON. Рекомендация counter_offer
при высоком score допустима; предложенная Python сумма ограничивается финансовой
математикой Go. Ответ rejected сам по себе не используется вместо Go-политики.

## Повтор проверки

[Запуск и тестовые команды](development.md). Тест TestRealScoringPipeline требует
TEST_SCORING_URL и TEST_DATABASE_URL; без первого он явно пропускается. Newman
с scoringMode=logreg_v1 проверяет те же исходы и ручные действия по реальному HTTP.

Остаётся настроить общий командный Compose и зафиксировать версию/digest scoring
для общей поставки. /health и JSON-ответ пока не содержат версию модели; backend
не выдумывает scoring_version, а версия подтверждается конфигурацией контейнера
и хешем предоставленного артефакта. Модель обучена на синтетических данных и
не является промышленным банковским скорингом.

## Достоверность входных данных

Успешный Python-ответ содержит только оценку и рекомендацию. Начиная с политики
go-demo-v3, неподтверждённые суммы не дают автоматического одобрения/контроффера.
Признак доверия относится к конкретной паре выручка/расходы из снимка, а не ко всей
компании. В тестах четырёх кредитных исходов финансовые факты подтверждаются
отдельно; дополнительно проверяется попытка повысить выручку без подтверждения.
Сохранённые v1/v2 результаты читаются без пересчёта.

Банк получает сохранённые decision, score, approvedAmountRub, reasons и все шесть
factors Python, а также локальные проверки и goDecision с версией политики.
model и modelVersion равны null, пока контракт сервиса не передаёт достоверные
метаданные. GET assessment не обращается к scoring. Внутренний комментарий банка
не входит в клиентский DTO.
