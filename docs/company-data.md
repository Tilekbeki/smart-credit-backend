# Компании, полномочия и достоверность данных

## Пользователь и компания

Глобальная роль пользователя — CLIENT или BANK_EMPLOYEE. Отдельная запись
`user_company_memberships` связывает CLIENT с каждой доступной компанией.
Пользователь может представлять несколько организаций, а организация — иметь
несколько представителей. Банк не получает фиктивное членство в компаниях.

| Членство | Полномочия |
| --- | --- |
| OWNER | Чтение, собственные черновики, submit, контакты, запросы исправлений, декларации, accept/decline |
| AUTHORIZED_REPRESENTATIVE | Те же операции кредитного MVP; отличие от OWNER сохранено для будущей политики представительства |
| VIEWER | Чтение компании и её отправленных заявок; никаких изменений |

В этом MVP выдавать, изменять и отзывать членство может только BANK_EMPLOYEE.
Владельцу не предоставлено право назначать представителей через клиентский API.
Производственное основание представительства потребует отдельного договора
интеграции и проверки полномочий; демонстрационный JWT этого не подтверждает.

GET `/api/v1/me/companies` возвращает список с membershipRole, version и
availableActions. Активную компанию выбирает frontend. POST recommendations и
POST applications принимают companyId. При одном действующем членстве его можно
опустить; при нескольких отсутствие даёт **409 company_required**. Backend никогда
не выбирает первую строку. Explicit null и некорректный UUID запрещены.

GET `/me` и OTP verify сохраняют совместимое companyId: UUID для единственного
членства, иначе null. Это удобство отображения, а не право доступа или JWT claim.
JWT идентифицирует пользователя через sub. Каждая операция повторно проверяет
актуальное членство по PostgreSQL; отзыв действует и для старого JWT.

GET applications без companyId возвращает доступные отправленные заявки всех
компаний и собственные черновики; фильтр companyId сужает выдачу. Чужой фильтр
возвращает пустую страницу. По UUID чужие заявки и документы возвращают 404.
Создатель заявки хранится в owner_id/userId, организация — в company_id/companyId.
Коллега по компании не видит чужой draft. Банк не видит draft, включая документы
и финансовые декларации, привязанные к этому draft. Отправленные заявки доступны
действующим представителям компании; accept/decline требуют права записи.

## Изменяемые сведения

| Категория | Операция | Гарантии |
| --- | --- | --- |
| Отображаемое имя и дополнительный email | PATCH `/me` | displayName отдельно от неизменяемого legalName; version и аудит |
| Телефон входа, юридическое ФИО | Изменение в MVP запрещено | Фиксированный OTP не доказывает владение реальным контактом |
| Контакты компании | PATCH `/companies/{id}` | Только contact.phone/email/address; версия компании и аудит |
| Регистрационные сведения | POST `/companies/{id}/change-requests` | whitelist, исходные/новые значения, причина, отдельное рассмотрение |
| Выручка и расходы | POST `/companies/{id}/financial-declarations` | client_declared, pending_review; исходные подтверждённые суммы сохраняются |
| Долг, платежи по кредитам, просрочки | Из клиентского API не изменяются | Синтетический источник БКИ, отдельный от декларации |

Контактный email не является подтверждённым email входа. В PATCH /me пустой
additionalEmail очищает дополнительный контакт; null запрещён. В контактном PATCH
компании передаются все три контактных поля. Неизвестные поля, дубли ключей,
некорректный UTF-8, неверные типы, пустые обязательные строки и превышение длины
отклоняются. Текст нормализуется удалением внешних пробелов; суммы — целые рубли
0..10¹². Для записей обязательна текущая версия, устаревшая даёт 409 version_conflict.

Безопасная смена телефона требует внешнего провайдера подтверждения, привязки
challenge к текущему пользователю и новому номеру, ограничений попыток, атомарного
погашения и изменения контакта с аудитом, уведомления прежнего контакта и политики
отзыва сессий. Production-интерфейс такого провайдера должен выдавать проверяемое
подтверждение владения конкретным номером. Эти операции пока не предоставлены
публичным API; использовать DEMO_OTP_CODE для реального номера нельзя.

## Исправление реквизитов

Клиент предлагает только name, inn, registrationNumber, registrationDate, okved,
directorName. Нельзя прислать произвольное имя SQL-колонки. Запрос хранит инициатора,
companyVersionAtRequest, originalValues, proposedValues, reason, status и сведения
о рассмотрении. История GET возвращает последние 100 записей, новые первыми.

Банк отдельно принимает или отклоняет запрос через
POST `/bank/companies/{companyId}/change-requests/{requestId}/review`.
Клиент может отменить pending_review через соответствующий `/cancel`.
Для рассмотрения и отмены version означает текущую версию компании; GET истории
возвращает её в companyVersion. Версия самой записи остаётся отдельным полем.
Статусы: pending_review → approved/rejected/cancelled. После завершения содержимое
и результат неизменяемы. Одновременные изменения сериализованы блокировкой компании.
При одобрении исходные реквизиты дополнительно сверяются с текущими, чтобы
устаревший запрос не затёр последующее исправление.

Одобрение атомарно меняет компанию, версию, запрос и аудит. Источник реквизитов
становится **bank_confirmed**, а не «подтверждено ФНС». Форматные проверки и
демонстрационный симулятор реестра не являются ответом государственного реестра.
Исправление реквизитов не выносит кредитное решение.

## Финансовое происхождение

`company_financial_declarations` хранит пару выручка/расходы, источник, статус,
время получения и подтверждения, инициатора и проверяющего, комментарий проверки,
возможную ссылку на документ и заявку. Каждая новая пара — отдельная запись;
старые значения и документы не заменяются. Подтверждённые записи неизменяемы.

Начальный demo_bank_feed помечается verified только в демонстрационном контексте.
Иные начальные данные — legacy_unverified/pending_review. Ввод клиента всегда
client_declared/pending_review. Значения, отличающиеся от подтверждённых, сохраняются
как декларации также при заполнении и изменении кредитного черновика.

Компания возвращает исходные/последние подтверждённые financials и
financialProvenance. Полная история, включая pending_review и rejected, доступна
отдельным GET. Для подтверждения банк вызывает
POST `/bank/companies/{companyId}/financial-declarations/{requestId}/review`
с outcome=approved или rejected и содержательной reason. Это отдельная операция
перед кредитным решением. verified требует reviewer и verifiedAt; происхождение
из клиентского ввода сохраняется. В представлении provenance такое подтверждение
обозначается bank_confirmed. Сам документ никогда не подтверждает введённые суммы.

Рекомендации возвращают financialVerificationRequired; для неподтверждённых сумм
платёжный бюджет ограничивается минимумом расчёта по анкете и исходным сведениям
компании. Рекомендация по-прежнему не гарантирует кредит.

Новое подтверждение заменяет текущий источник для последующих заявок; прежняя
запись остаётся историей. Нельзя выбрать старую более высокую выручку и выдать её
за актуальную после подтверждения новых, меньших показателей.

Submit фиксирует выбранные суммы и актуальное подтверждение **точно этих значений**
в неизменяемом снимке. При отсутствии подтверждения нужна выписка для любого
продукта. Python получает заявленные числа из снимка; Go не заменяет их живыми
данными. Высокий score и загруженная выписка не позволяют автоодобрение:
неподтверждённые показатели требуют manual_review либо строгого отказа по
обязательным ограничениям. Перед ручным одобрением backend отдельно проверяет
подтверждённую запись с точными суммами отправленного снимка. Увеличение выручки
после submit не меняет ни снимок, ни исходный scoring.

## Версии, повторы, аудит и миграция

Для PATCH используются версии и транзакции. Для остальных новых изменений
(включая банковский PUT членства) обязателен UUID Idempotency-Key. Ключ действует
24 часа в области пользователя, операции, компании и целевого объекта. Повтор
с тем же нормализованным телом возвращает прежний статус/тело до проверки версии;
другое тело с тем же ключом — 409 idempotency_conflict. Доступ проверяется перед
replay. Старые гарантии manual/accept/decline сохранены; customerExplanation,
если задан, включается в каноническое тело. Отсутствие/пустое объяснение сохраняет
старую канонизацию и включает стандартную публичную причину.

Общий `data_audit_events` содержит пользователя, компанию, объект, старые/новые
значения, причину и время. DELETE/UPDATE аудита запрещены триггером. Членство не
удаляется: revoke меняет статус, повторный grant использует тот же ID с новой
версией. Для записи бизнес-операции используется FOR SHARE действующего членства;
отзыв ждёт завершения этой транзакции. Черновики и бизнес-операции проверяются
также внутри PostgreSQL repository, а не только в HTTP middleware.

Миграции 000012–000014 расширяют схему и переносят прежние связи users.company_id.
Составной FK заявки теперь ссылается на сохранённую пару user/company членства,
а creator и company имеют собственные FK. Документ получает company_id с составным
FK на заявку. История, решения, файлы и idempotency responses не пересоздаются.
Старая users.company_id оставлена как deprecated, в авторизации не используется.

Перед обновлением сохраните резервную копию PostgreSQL и файлового volume,
остановите **все старые экземпляры** backend, примените миграции и запустите новый
образ. Совместный запуск старого и нового кода при многокомпанейной модели не
поддерживается. Down-миграции намеренно блокируются: безопасный откат — проверенная
резервная копия и соответствующая версия приложения. Новые членства и подтверждения
нельзя молча удалить ради возврата к старой схеме.
